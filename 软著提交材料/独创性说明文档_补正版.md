## 一、软件概述

本软件是面向 SaaS 多租户商业场景的人工智能服务集成框架，核心技术栈为 TypeScript + Next.js 14（App Router）+ Prisma ORM，部署于 Pi Network 区块链生态。软件提供三大核心能力：

**（一）多提供商 AI 服务路由：** 将 OpenAI、Anthropic Claude 和 Ollama 本地大模型统一抽象为单一接口，通过自动容错降级机制保证 AI 服务的高可用性，使商户无需关心底层 AI 服务的稳定性差异。

**（二）Pi Network 区块链原生支付：** 基于 Pi Platform API V2 构建完整的 U2A（User-to-App）支付生命周期管理，包含创建、审批、链上确认、完成的全流程闭环，并集成幂等性保护和孤儿支付处理机制。

**（三）企业级多租户服务治理：** 基于 Node.js AsyncLocalStorage 的租户上下文隔离机制配合 Prisma 中间件自动注入数据边界，辅以离线 License 授权验证和微秒级用量统计，构成完整的 SaaS 服务治理体系。

本软件并非通用脚手架的简单组合，而是针对 Pi Network 生态商业化场景定制开发的专属框架。其核心创新价值体现在以下五个技术模块中，每个模块均有大量原创设计决策和针对性技术突破，与任何已有开源框架存在本质区别。

## 二、核心创新点

### 创新点一：AI 多提供商智能路由系统

**【技术问题】**

在企业 AI 服务集成实践中，存在以下尚未被现有方案彻底解决的工程问题：

1. **单点依赖风险：** 绑定单一 AI 提供商（如 OpenAI）时，一旦该提供商服务中断或 API Key 超额，整个应用立即不可用，无法自动恢复。
2. **流式响应切换困难：** SSE（Server-Sent Events）流式推送建立在长连接之上，传统手动重试方案会导致前端 EventSource 断开，用户体验极差。
3. **接口碎片化：** 各 AI 提供商 API 格式差异显著（OpenAI 的 `choices[0].message.content`、Anthropic 的 `content[0].text`、Ollama 的 `message.content`），直接调用导致业务代码与提供商 SDK 强耦合。

**【创新解决方案】**

本软件独创了"三层解耦 + 自动容错链"的 AI 路由架构：

- **第一层（接口契约层）：** 以 Strategy 设计模式定义统一的 `AIProvider` 接口，规范 `chat()`、`stream()`、`isAvailable()`、`healthCheck()` 四个行为，所有提供商实现此接口后即可在运行时互相替换；
- **第二层（行为模板层）：** 以 Template Method 设计模式实现 `BaseAIProvider` 抽象基类，将超时控制（AbortController + setTimeout）、HTTP 错误处理、结构化日志固化在基类中，子类只需覆写 `executeChat()` 和 `executeStream()` 两个纯业务方法；
- **第三层（路由调度层）：** `AIProviderFactory` 实现双模式路由：若请求明确指定提供商则直连（不触发 fallback），否则按 `AI_PRIMARY_PROVIDER` → `AI_FALLBACK_PROVIDERS` 顺序依次尝试，每次失败均记录跳过原因，最终附带完整路由决策信息（`RoutingDecision`）返回响应，便于运维排查。

**【技术实现——关键代码片段】**

以下摘自 `packages/pi-sdk/src/ai-providers/factory.ts`，展示路由核心逻辑（共约 80 行，此处摘录核心部分）：

```typescript
// AIProviderFactory.route() — 主提供商 + 自动 fallback 链
async route(
  request: AIProviderRequest,
  requestedProvider?: AIProviderName
): Promise<AIProviderResponse & { routing: RoutingDecision }> {
  const routeStart = Date.now();
  const skipped: Array<{ provider: AIProviderName; reason: string }> = [];

  // 场景1：请求级别指定提供商 → 直连，不 fallback
  if (requestedProvider) {
    const provider = this.providers.get(requestedProvider);
    if (!provider) throw new Error(`Unknown AI provider: ${requestedProvider}`);
    if (!provider.isAvailable()) {
      throw new Error(
        `AI provider '${requestedProvider}' is not available (missing API key or disabled)`
      );
    }
    const response = await provider.chat(request);
    return {
      ...response,
      routing: {
        requested: requestedProvider,
        actual: requestedProvider,
        fallback: false,
        routingTimeMs: Date.now() - routeStart,
      },
    };
  }

  // 场景2：主提供商 + fallback 链
  const providersToTry: AIProviderName[] = [
    this.primaryProvider,
    ...this.fallbackOrder.filter((name) => name !== this.primaryProvider),
  ];

  let lastError: Error | null = null;

  for (const providerName of providersToTry) {
    const provider = this.providers.get(providerName);

    if (!provider) {
      skipped.push({ provider: providerName, reason: 'not registered' });
      continue;
    }
    if (!provider.isAvailable()) {
      skipped.push({ provider: providerName, reason: 'not available' });
      continue;
    }

    try {
      const response = await provider.chat(request);
      const isFallback = providerName !== this.primaryProvider;

      if (isFallback) {
        logWarn('AI request fell back to alternate provider', {
          primary: this.primaryProvider,
          actual: providerName,
          skipped,
        });
      }

      return {
        ...response,
        routing: {
          requested: undefined,
          actual: providerName,
          fallback: isFallback,
          skippedProviders: skipped,
          routingTimeMs: Date.now() - routeStart,
        },
      };
    } catch (err) {
      lastError = err instanceof Error ? err : new Error(String(err));
      skipped.push({ provider: providerName, reason: lastError.message });
      logError(`AI provider '${providerName}' failed, trying next`, lastError);
    }
  }

  // 所有提供商均失败
  throw lastError ?? new Error('No AI providers available');
}
```

```typescript
// BaseAIProvider.chat() — 超时控制 + 统一错误处理
async chat(request: AIProviderRequest): Promise<AIProviderResponse> {
  if (!this.isAvailable()) {
    throw new Error(`${this.getDisplayName()} is not configured or not available`);
  }

  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), this.config.timeout);

  try {
    const response = await this.executeChat(request, controller.signal);
    logEvent(`${this.getDisplayName()} response generated`, {
      provider: this.name,
      model: response.model,
      promptTokens: response.usage?.promptTokens,
      completionTokens: response.usage?.completionTokens,
    });
    return response;
  } catch (error) {
    if (error instanceof Error && error.name === 'AbortError') {
      const timeoutError = new Error(
        `${this.getDisplayName()} request timed out after ${this.config.timeout}ms`
      );
      logError(timeoutError.message, null, { provider: this.name, timeout: this.config.timeout });
      throw timeoutError;
    }
    throw error;
  } finally {
    clearTimeout(timeoutId);
  }
}
```

### 创新点二：Pi Network U2A 支付生命周期管理

**【技术问题】**

Pi Network 的 U2A（User-to-App）支付协议与传统 Web2 支付网关存在根本差异：

1. **双向确认机制：** Pi 支付要求应用服务器分别调用 `/approve`（审批）和 `/complete`（完成）两个 Pi Platform API 端点，且两次调用均需在特定时序内完成，否则 Pi SDK 将永久死锁，无法释放用户钱包资金。
2. **幂等性挑战：** 区块链交易的不可逆性要求服务端在 `approve` 和 `complete` 两个阶段都必须实现幂等处理，防止网络重试导致重复计费或订单状态紊乱。
3. **孤儿支付问题：** 前端可能在订单尚未同步到服务端时就发起 `approve` 请求，此时若盲目创建支付记录，会产生与任何订单无关联的"孤儿支付"，导致数据不一致。

**【创新解决方案】**

本软件独创了"先 Pi 后本地"的三阶段原子化支付处理流程：

- **审批阶段（approve）：** 先查询本地订单状态，仅当订单存在时才创建 Payment 行（孤儿支付保护）；随后无论本地操作是否执行，都必须调用 Pi Platform API `/approve`，否则用户钱包会被锁定；对 Pi API 返回 `already approved` 的幂等错误进行宽容处理，允许放行。
- **完成阶段（complete）：** 先调用 Pi Platform API `/complete` 提交链上 txid，再以 Prisma 事务原子性更新本地 Payment、Order、Membership 三张表；若本地已完成（`status === 'COMPLETED'`），则直接返回成功（幂等边界）。
- **取消阶段（cancel）：** 原子性更新 Payment 和关联 Order 的状态，防止已取消支付被重复完成。

**【技术实现——关键代码片段】**

以下摘自 `apps/web/src/app/api/payments/approve/route.ts`，展示孤儿支付保护与 Pi API 容错：

```typescript
// POST /api/payments/approve — 孤儿支付保护 + Pi API 强制调用
async function __POST(req: Request) {
  const { paymentId, orderId } = await req.json();
  if (!paymentId) {
    return NextResponse.json({ success: false, error: 'Missing paymentId' }, { status: 400 });
  }

  // 幂等检查：查询本地是否已存在该支付记录
  const existingPayment = await prisma.payment.findUnique({
    where: { piPaymentId: paymentId },
  });

  // 孤儿支付保护：仅当 orderId 对应的订单存在时才创建 Payment 行
  if (!existingPayment) {
    const order = await prisma.order.findUnique({ where: { orderNo: orderId } });
    if (order) {
      await prisma.payment.create({
        data: {
          orderId: order.id,
          piPaymentId: paymentId,
          amount: order.amount,
          status: 'PENDING',
          developerApproved: true,
          approvedAt: new Date(),
          memo: `Paying for order ${order.orderNo}`,
        },
      });
      await prisma.order.update({
        where: { id: order.id },
        data: { status: 'PENDING_APPROVAL', paymentId: paymentId },
      });
    }
    // 若 order 不存在：不创建孤儿 Payment，但仍必须调用 Pi API
  }

  // 无论本地操作如何，Pi Platform Approve 必须调用，否则 SDK 死锁
  const piRes = await fetch(`${piApiBase}/v2/payments/${paymentId}/approve`, {
    method: 'POST',
    headers: { Authorization: `Key ${process.env.PI_API_KEY}` },
  });

  if (!piRes.ok) {
    const errText = await piRes.text();
    // 幂等宽容：已审批过视为成功
    if (!errText.includes('already approved')) {
      return NextResponse.json(
        { success: false, error: `Pi API Error: ${errText}` },
        { status: 502 }
      );
    }
  }
  return NextResponse.json({ success: true });
}
```

```typescript
// POST /api/payments/complete — 先 Pi 后本地 + 事务原子性
async function __POST(req: Request) {
  const { paymentId, txid } = await req.json();

  // 先调用 Pi Platform Complete（提交链上确认）
  const piRes = await fetch(`${piApiBase}/v2/payments/${paymentId}/complete`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: `Key ${apiKey}` },
    body: JSON.stringify({ txid }),
  });

  if (!piRes.ok) {
    const errText = await piRes.text();
    if (!errText.includes('already completed')) {
      return NextResponse.json(
        { success: false, error: `Pi API Error: ${errText}` },
        { status: 502 }
      );
    }
  }

  // 幂等边界：本地已完成则直接返回
  const payment = await prisma.payment.findUnique({
    where: { piPaymentId: paymentId },
    include: { order: true },
  });
  if (!payment || payment.status === 'COMPLETED') {
    return NextResponse.json({ success: true, message: 'Already completed locally' });
  }

  // Prisma 事务：Payment + Order + Membership 原子更新
  await prisma.$transaction(async (tx) => {
    await tx.payment.update({
      where: { piPaymentId: paymentId },
      data: {
        txid,
        status: 'COMPLETED',
        transactionVerified: true,
        developerCompleted: true,
        completedAt: new Date(),
      },
    });
    const updatedOrder = await tx.order.update({
      where: { id: payment.orderId },
      data: { status: 'COMPLETED' },
    });
    // 自动开通/续期会员资格（30天周期）
    const endAt = new Date();
    endAt.setDate(endAt.getDate() + 30);
    await tx.customerMembership.create({
      data: {
        customerId: updatedOrder.customerId,
        membershipId: (await ensureMembership(tx, updatedOrder)).id,
        startAt: new Date(),
        endAt,
        status: 'ACTIVE',
      },
    });
  });
  return NextResponse.json({ success: true });
}
```

### 创新点三：多租户数据硬隔离机制

**【技术问题】**

传统 SaaS 多租户架构在数据层面面临以下挑战：

1. **开发者遗漏过滤条件：** 在每个 Prisma 查询中手动添加 `where: { merchantId }` 极易遗漏，一旦遗漏即产生跨租户数据泄露；
2. **异步上下文传递：** Node.js 异步编程中，请求级别的 `merchantId` 需要跨多个 `await` 边界传递，使用函数参数传递会导致签名污染，使用全局变量则无法在并发场景下正确隔离；
3. **Edge Runtime 兼容性：** 部分 Next.js 中间件运行在 Vercel Edge Runtime，不支持 Node.js 专属 API（如 `async_hooks`），需要降级处理。

**【创新解决方案】**

本软件独创了"AsyncLocalStorage + Prisma 中间件"的双层硬隔离架构：

- **上下文层：** 使用 Node.js `AsyncLocalStorage<string>` 存储请求作用域内的 `merchantId`，该值自动跟随异步调用链传播，无需修改任何业务函数签名，且跨 `await` 不泄漏；同时为 Edge Runtime 提供透明降级实现（`getStore()` 返回 `undefined`，`run()` 直接执行回调）；
- **数据层：** `applyTenantMiddleware(prisma)` 向 Prisma 客户端注册全局中间件，拦截 7 类租户敏感模型（`Customer`、`Order`、`Payment`、`Booking`、`Membership`、`Service`、`GenerationHistory`）上的所有 `find*`、`update*`、`delete*` 操作，自动将 AsyncLocalStorage 中的 `merchantId` 注入到 `where` 子句中；
- **安全边界：** 中间件明确维护需隔离模型的白名单，非白名单模型不注入，避免误伤系统级查询；对异常结构进行 try-catch 保护，防止中间件本身成为故障点。

```typescript
// 运行时自适应：Node.js 环境加载 AsyncLocalStorage，Edge Runtime 降级
let tenantStore: TenantStore | undefined;
try {
  if (typeof process !== 'undefined' && process.versions) {
    // 使用 eval('require') 避免 Webpack/Next.js 打包时静态分析报错
    const r = eval('require') as (moduleName: string) => unknown;
    const asyncHooks = r('async_hooks') as {
      AsyncLocalStorage: new <T>() => {
        getStore: () => T | undefined;
        run: (store: T, fn: () => unknown) => unknown;
      };
    };
    tenantStore = new asyncHooks.AsyncLocalStorage<string>();
  }
} catch (_e) {
  // Edge Runtime 降级：getStore() 始终返回 undefined，run() 直接执行
  tenantStore = {
    getStore: () => undefined,
    run: (_id: string, fn: () => unknown) => fn(),
  };
}

export const getTenantId = (): string | undefined => tenantStore?.getStore();
export const runWithTenant = <T>(id: string, fn: () => T): T => tenantStore!.run(id, fn) as T;
```

```typescript
// Prisma 中间件：自动向白名单模型注入 merchantId 过滤条件
export function applyTenantMiddleware(prisma: PrismaClient) {
  prisma.$use(async (params, next) => {
    const tenantId = getTenantId();

    const modelsRequiringIsolation = [
      'Customer',
      'Order',
      'Payment',
      'Booking',
      'Membership',
      'Service',
      'GenerationHistory', // AI 生成记录必须按租户隔离，防止跨商户数据泄露
    ];

    try {
      if (tenantId && params.model && modelsRequiringIsolation.includes(params.model)) {
        params.args = params.args || {};

        if (
          [
            'findUnique',
            'findFirst',
            'findMany',
            'update',
            'updateMany',
            'delete',
            'deleteMany',
          ].includes(params.action)
        ) {
          params.args.where = { ...params.args.where, merchantId: tenantId };
        }
      }
    } catch (_e) {
      // 中间件异常不阻断请求，上游应记录告警
    }

    return next(params);
  });
}
```

### 创新点四：License 离线授权验证机制

**【技术问题】**

企业级 SaaS 软件的授权验证面临以下矛盾：

1. **联网验证的可用性风险：** 若授权中心服务不可用，会导致已付费客户的生产服务中断；
2. **功能分级的精细控制：** 不同套餐（Starter / Professional / Enterprise）对应不同功能集合，需要在代码层面强制执行，防止越权使用；
3. **开发环境便利性：** 开发阶段不应因缺少生产 License 而导致功能受限，同时开发环境的宽松策略不能泄露到生产环境。

**【创新解决方案】**

本软件独创了"双环境策略 + HMAC-SHA256 离线签名验证"的 License 体系：

- **签名算法层：** 以 `[licenseId, issuedTo, merchantId, issuedAt, expiresAt, tier, features.sort().join(','), maxRequestsPerMonth, maxTenants]` 拼接为 pipe 分隔的待签名字符串，使用 Web Crypto API 的 `crypto.subtle.verify()` 进行 HMAC-SHA256 验签，字段顺序严格固定以防止签名绕过；
- **缓存层：** 以 License ID 为 key 在内存中缓存验证结果，TTL 为 5 分钟，避免每次请求都重复执行密码学运算；
- **功能门控层：** `TIER_FEATURES` 常量定义三级套餐对应的功能白名单（`starter: ['ai_routing']`、`professional: [+ streaming, usage_tracking, webhook_monitoring]`、`enterprise: [+ multi_tenant, advanced_analytics]`），`hasFeature()` 在运行时对照检查；
- **双环境策略：** 开发环境（`NODE_ENV !== 'production'`）自动颁发企业级许可并跳过签名验证；生产环境强制验签，License 过期或签名无效均返回 403。

```typescript
/** 构建 License 待签名字符串（字段顺序严格固定） */
export function buildSignablePayload(license: SerializedLicense): string {
  return [
    license.id,
    license.issuedTo,
    license.merchantId,
    license.issuedAt,
    license.expiresAt,
    license.tier,
    license.features.sort().join(','), // sort() 确保顺序一致性
    license.maxRequestsPerMonth?.toString() ?? '',
    license.maxTenants?.toString() ?? '',
  ].join('|');
}

/** 使用 Web Crypto API（HMAC-SHA256）验证签名 */
export async function verifySignature(
  payload: string,
  signature: string,
  publicKey: string
): Promise<boolean> {
  try {
    const keyData = Uint8Array.from(atob(publicKey), (c) => c.charCodeAt(0));
    const cryptoKey = await crypto.subtle.importKey(
      'raw',
      keyData,
      { name: 'HMAC', hash: 'SHA-256' },
      false,
      ['verify']
    );
    const encoder = new TextEncoder();
    const sigBuffer = Uint8Array.from(atob(signature), (c) => c.charCodeAt(0));
    return await crypto.subtle.verify('HMAC', cryptoKey, sigBuffer, encoder.encode(payload));
  } catch {
    return false; // 签名格式错误视为无效
  }
}
```

```typescript
const CACHE_TTL_MS = 5 * 60 * 1000; // 缓存有效期：5 分钟
const cache = new Map<string, CachedLicense>();

export async function verifyAndCacheLicense(
  rawLicense: SerializedLicense,
  skipSignatureCheck = false
): Promise<LicenseValidationResult> {
  const cacheKey = rawLicense.id;
  const now = Date.now();

  // 命中缓存则直接返回，避免重复执行密码学运算
  const cached = cache.get(cacheKey);
  if (cached && now - cached.cachedAt < CACHE_TTL_MS) {
    return cached.result;
  }
  // 缓存未命中：执行完整验证流程
  const result = await validateLicense(rawLicense, { skipSignatureCheck });
  cache.set(cacheKey, { result, cachedAt: now });
  return result;
}
```

### 创新点五：微秒级用量统计与内存缓冲架构

**【技术问题】**

传统 SaaS 用量统计方案存在以下性能瓶颈：

1. **每次调用同步写数据库：** 每个 AI 请求完成后立即执行 `INSERT INTO usage_records`，在高并发场景下（100+ QPS）成为数据库写入瓶颈；
2. **配额超限检查延迟：** 配额超限告警依赖数据库聚合查询，响应延迟高（100ms+），无法实现实时拦截；
3. **观测性缺失：** 缺乏对 AI 请求成功率、各提供商使用分布、平均延迟等指标的结构化追踪。

**【创新解决方案】**

本软件独创了"内存缓冲 + 月度计数器 + 定时 Flush"三层异步用量追踪架构：

- **内存缓冲层：** 所有用量事件（`trackUsage()`）同步写入进程内 `buffer: UsageRecord[]` 数组，完全无 IO 阻塞，单次记录耗时在微秒级；
- **月度计数器：** 以 `${tenantId}:YYYY-MM` 为 key 维护 `Map<string, number>` 计数器，`checkQuota()` 直接读取内存，无数据库往返，实现毫秒级配额实时检查；
- **智能 Flush 策略：** 正常情况下以 60 秒间隔定时批量 Flush 至 Webhook 审计系统；当缓冲区达到 `MAX_BUFFER_SIZE = 500` 条时立即触发紧急 Flush，防止内存溢出；Flush 函数以 `void` 方式调用，不阻塞当前请求；
- **配额预警机制：** `checkQuota()` 在使用率超过 80% 时标记 `warning: true`，上层中间件可据此触发邮件或 Webhook 告警，在用量耗尽前提前介入。

**【技术实现——关键代码片段】**

以下摘自 `packages/pi-sdk/src/usage/tracker.ts`，展示内存缓冲核心逻辑：

```typescript
// 进程内缓冲区：无 IO 阻塞，微秒级写入
const buffer: UsageRecord[] = [];
// 月度计数器：毫秒级配额查询
const monthlyCounters = new Map<string, number>();

const MAX_BUFFER_SIZE = 500; // 超出时触发紧急 Flush
const DEFAULT_FLUSH_INTERVAL_MS = 60 * 1000; // 正常 Flush 间隔：60 秒

export function trackUsage(params: {
  tenantId: string;
  merchantId: string;
  type: UsageEventType;
  tokensUsed?: number;
  provider?: string;
  model?: string;
  latencyMs?: number;
  success: boolean;
  error?: string;
  metadata?: Record<string, unknown>;
}): UsageRecord {
  const record: UsageRecord = {
    id: `usage_${Date.now()}_${Math.random().toString(36).slice(2, 9)}`,
    timestamp: new Date(),
    ...params,
  };

  buffer.push(record); // 同步写入内存，无 IO

  // 更新月度计数器
  const key = `${params.tenantId}:${new Date().getFullYear()}-${String(
    new Date().getMonth() + 1
  ).padStart(2, '0')}`;
  monthlyCounters.set(key, (monthlyCounters.get(key) ?? 0) + 1);

  // 缓冲区过大时立即触发异步 Flush（不阻塞当前请求）
  if (buffer.length >= MAX_BUFFER_SIZE) {
    void flushToWebhook();
  }

  return record;
}

export function checkQuota(
  tenantId: string,
  merchantId: string,
  maxRequestsPerMonth: number
): QuotaStatus {
  const key = `${tenantId}:${new Date().getFullYear()}-${String(new Date().getMonth() + 1).padStart(
    2,
    '0'
  )}`;
  const used = monthlyCounters.get(key) ?? 0;
  const percentage = maxRequestsPerMonth > 0 ? Math.round((used / maxRequestsPerMonth) * 100) : 0;

  return {
    tenantId,
    merchantId,
    used,
    limit: maxRequestsPerMonth,
    percentage,
    exceeded: used >= maxRequestsPerMonth,
    warning: percentage >= 80, // 80% 阈值预警
    resetAt: getMonthResetDate(),
  };
}
```
